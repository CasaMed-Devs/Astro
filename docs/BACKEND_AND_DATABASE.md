# Astro101 — Backend & Database, Explained Simply

This document explains how the "invisible" half of the app works: the backend server and the database. No code-reading required — everything here is in plain language, with the technical name mentioned alongside so you can search for it later if needed.

---

## 1. The Big Picture

Think of Astro101 as three separate pieces that talk to each other:

```
┌─────────────────┐         ┌──────────────────┐         ┌───────────────────┐
│                  │         │                   │         │                    │
│   Your Phone     │ ◄─────► │  Our Backend       │ ◄─────► │  Outside Services   │
│   (the app)      │         │  Server            │         │  (Firebase, AI,     │
│                  │         │  (functions/)       │         │   Razorpay, etc.)  │
└─────────────────┘         └──────────────────┘         └───────────────────┘
        │                                                          ▲
        └──────────────────────────────────────────────────────────┘
              (the app ALSO talks straight to Firebase for some things)
```

- **Your Phone** — the React Native app you see and tap on.
- **Our Backend Server** — a small program we wrote (lives in the `functions/` folder) that runs either on your computer (for testing) or eventually on Google's servers (for real users). It's the "brain" that does anything sensitive or complicated.
- **Outside Services** — companies/tools we didn't build, that we plug into: Firebase (Google's app toolkit), an AI provider (like OpenAI), an astrology-calculation service, and Razorpay (payments).

**Why not have the phone talk directly to everything?** Two reasons:
1. **Secrets** — things like the AI API key or Razorpay's secret key must never sit inside the app itself, because anyone could extract them by taking the app apart. The backend holds those secrets; the phone never sees them.
2. **Trust** — the phone can't be trusted to tell the truth about things like "the payment succeeded" or "I only used 2 messages." The backend double-checks everything important.

## 2. What the Backend Actually Does

The backend is a small web server (built with a tool called **Express**, written in **TypeScript**). It exposes a handful of "doors" (called **endpoints** or **routes**) that the phone can knock on. Here's every one of them, in plain terms:

| What it's for | Door (endpoint) | Who can use it | What happens |
|---|---|---|---|
| Health check | `GET /health` | Anyone | Just replies "I'm alive" — used to confirm the server is running |
| Today's horoscope | `GET /horoscopes/:sign/today` | Anyone | Returns a daily horoscope for a zodiac sign, generated by AI once per day and then reused |
| Send a chat message | `POST /chats/:chatId/messages` | Logged-in users only | Takes your message, checks you have enough credits (or an active subscription), asks the AI to reply as the chosen astrologer, saves the reply |
| Start a subscription payment | `POST /payments/subscription/order` | Logged-in users only | Creates a Razorpay "order" (an official request to charge money) |
| Confirm a subscription payment | `POST /payments/subscription/verify` | Logged-in users only | Double-checks the payment was real (not faked by the phone), then marks the subscription active |
| Start a report payment | `POST /payments/report/order` | Logged-in users only | Same idea, but for the one-time kundali report purchase |
| Confirm a report payment | `POST /payments/report/verify` | Logged-in users only | Verifies payment, then triggers the AI to actually write the report |
| Razorpay tells us what happened | `POST /webhooks/razorpay` | Razorpay's own servers | Razorpay calls this automatically when a subscription renews, gets cancelled, or a payment fails |
| Delete my account | `POST /account/delete` | Logged-in users only | Wipes your data from the database and deletes your login |

**"Logged-in users only"** means the phone has to prove who it is by sending a security token (like showing an ID card) with every request. That token is a JWT the backend itself issues after verifying an SMS OTP (sent via voicenSMS) — not a Firebase login — and the backend checks that token itself before doing anything.

## 3. Two Ways the Backend Runs (Same Code, Different "Shell")

This might be the part that's most confusing, so here's the plain-English version:

We wrote the actual logic **once**. Then we wrap it in two different "shells" depending on where it's running:

- **`server.ts`** — the shell used when you run it on your own computer for testing (`npm run backend:dev`). It just starts a normal web server on your machine, listening on port 3000.
- **`index.ts`** — the shell used when it's deployed to **Firebase Cloud Functions** (Google's servers) for real users. Same exact logic, just running on Google's infrastructure instead of your laptop.

This means: **you don't have to deploy anything to Firebase to test the app.** Running it locally is fully functional and talks to the real Firebase/database — it's just running from your computer instead of Google's. Deployment (`firebase deploy --only functions`) is a later step, for when real users need to use the app without your computer being turned on.

## 4. The Astrologers Are AI, Not Real People

This is a core design decision, worth spelling out clearly: **there are no real human astrologers behind this app.** Each "astrologer" you see in the app (Pandit Ramesh Shastri, Meera Iyer, etc.) is really an **AI persona** — a distinct character/personality we describe to an AI model (like OpenAI's GPT or Anthropic's Claude) so it responds in that style.

- The list of personas (their names, specialties, languages, and — importantly — their secret "personality instructions") lives in `functions/src/config/personas.ts`.
- When you chat, the backend picks the persona's instructions, adds your recent conversation, and asks the AI provider to generate a reply "in character."
- **Which AI company we use is a switch, not a hardcoded choice** — set one environment variable (`AI_PROVIDER=openai` or `AI_PROVIDER=anthropic`) plus the matching key, and it works. Until a key is provided, the app returns a clear "temporarily unavailable" message instead of pretending to work.

## 5. The Kundali Report — How It's Actually Calculated

This part is worth explaining because it's more sophisticated than it might seem: the report is **not** the AI just making things up from your birthday. Here's the real pipeline:

1. You've entered your **date of birth, time of birth, and place of birth**.
2. The backend sends your place of birth to a **geocoding service** (part of FreeAstrologyAPI.com) to convert "Jaipur, Rajasthan" into exact map coordinates (latitude/longitude) and a timezone.
3. Using your exact birth date/time + those coordinates, the backend calls a **real Vedic astrology calculation engine** (also FreeAstrologyAPI.com) to compute:
   - **Planetary positions** — where the Sun, Moon, Mars, etc. actually were in the sky at your exact birth moment, and which astrological "house" each one falls in.
   - **Vimsottari Dasha periods** — the traditional Vedic timeline of which planet "rules" which years of your life.
4. All of that **real, calculated data** is handed to the AI, along with your name and gender, with instructions to write a warm, readable report **grounded in the actual chart** — not invent random predictions.
5. The finished report text is saved to the database, and the app shows it to you.

So: the astrology math is real and calculated properly; the AI's job is only to turn that math into a nicely written, personalized report — not to invent the astrology itself.

## 6. The Database — What's Stored and Where

We use **Cloud Firestore**, which is Google's "NoSQL" database — instead of spreadsheet-style tables, think of it as folders and documents (like a very organized filing cabinet). Here's every "folder" (called a **collection**) and what's inside each "file" (called a **document**):

### `users` — one document per person
```
users/{your user ID}
  - name              your display name
  - phoneNumber       your phone number
  - dateOfBirth        e.g. "13/01/2000"
  - timeOfBirth         e.g. "05:47 AM"
  - placeOfBirth        e.g. "Udaipur, Rajasthan"
  - gender               female / male / other
  - credits              how many free AI messages you have left
  - fcmTokens            device IDs used to send you push notifications
```
**Important security detail:** the `credits` number can only ever be changed by the backend, never by the app directly. This stops anyone from hacking the app to give themselves unlimited free messages.

### `chats` — one document per conversation
```
chats/{chat ID}
  - userId        which user this chat belongs to
  - personaId      which AI astrologer you're talking to
  - lastMessage    a preview of the latest message

chats/{chat ID}/messages/{message ID}   (a sub-folder inside each chat)
  - sender     "user" (you) or "astrologer" (the AI)
  - text        the actual message
  - status      sent / delivered
```
**Security detail:** you can write messages as yourself ("user"), but you can **never** write a message pretending to be the astrologer — only the backend is allowed to do that, which stops anyone from faking AI replies.

### `subscriptions` — one document per user
```
subscriptions/{your user ID}
  - planId                     which plan (e.g. "Astro101 Plus")
  - status                     active / pending / cancelled / expired / failed
  - razorpaySubscriptionId     Razorpay's reference for this subscription
  - currentPeriodStart/End     when the current billing period runs
```
Only the backend can write to this — never the app directly, so a phone can't just fake "I paid" to unlock features.

### `payments` — one document per payment attempt
```
payments/{payment ID}
  - userId       who paid
  - orderId       Razorpay's order reference
  - purpose        "subscription" or "report"
  - status          created / paid / failed / refunded
```

### `reports` — one document per user
```
reports/{your user ID}
  - status         pending / ready / failed
  - content         the actual written report text (once ready)
  - generatedAt     when it finished
```

### `horoscopes` — shared, public content
```
horoscopes/{zodiac sign}/daily/{date}
  - content   today's horoscope text for that sign
```
This is generated once per sign per day (not separately for every user) and cached, so we're not paying the AI to write the same horoscope 1,000 times.

### Notably **not** in the database
The list of AI astrologer personas and the subscription pricing plans are **not** stored in the database at all — they live directly in the code (`personas.ts`, `plans.ts`). That's a deliberate choice: changing a persona's personality or a price doesn't need a database migration, just an edit + redeploy.

## 7. Who's Allowed to Do What (Security Rules)

Firestore has a rules file (`firestore.rules`) that acts like a bouncer — it checks every single read/write request against a checklist **before** the database allows it, regardless of what the app's code says. This matters because a clever user could bypass the app entirely and try to talk to the database directly — the rules are what actually stop them, not the app's good behavior.

The short version of our rules:
- You can only read **your own** profile, chats, subscription, payments, and report — never anyone else's.
- You can create your own user profile, but it must start with 0 credits (real credits are granted by the backend afterward, automatically).
- You can send chat messages as yourself, but never fake a reply from the astrologer.
- You **cannot** directly edit your subscription, payment records, or report — only the backend can, since these represent things that must be verified as true (did you actually pay? did the AI actually finish writing?).
- Horoscopes are public — anyone can read them, nobody but the backend can write them.

## 8. How Money and Trust Flow (Payments)

This app uses **Razorpay** for payments. The important design rule: **the phone is never trusted to declare a payment successful.**

Here's the actual flow for, say, unlocking the kundali report:

1. Phone asks backend: "I want to pay for the report."
2. Backend creates an official Razorpay "order" (like a bill) and gives the phone just enough info to show the payment screen.
3. You pay through Razorpay's own secure checkout screen (never our code, never our servers see your card details).
4. Razorpay gives the phone a receipt with a **cryptographic signature** — a tamper-proof stamp.
5. The phone sends that receipt back to our backend.
6. **The backend re-calculates the expected signature itself and compares it.** Only if they match exactly does the backend consider the payment real. This stops someone from hacking the phone app to just claim "I paid" without actually paying.
7. Only after that check passes does the backend unlock the report / mark the subscription active.

Razorpay also calls our backend directly (the "webhook") whenever something happens on their end later — like a subscription renewing next month, or a card payment failing — so our records stay accurate even without the user opening the app.

## 9. Credits & Free Usage — How Overspending Is Prevented

New users get a starter number of free AI messages ("credits"). Here's how we make sure nobody can cheat this:

1. When your account is first created, a small automatic piece of backend code (a **Firestore trigger**, `onUserCreated.ts`) fires immediately and sets your starting credit balance — **the app itself never sets this number**, so there's no way to fake a huge starting balance.
2. Every time you send a chat message, the backend:
   - Checks if you have an **active subscription** — if so, no credits are touched (unlimited messages).
   - If not, it checks your credit balance and the message's cost (some AI personas cost more credits per message than others), and subtracts credits **only if you actually have enough** — done as a single atomic database operation so two messages sent at the exact same moment can't both sneak through when you only had enough credits for one.
3. If you're out of credits and not subscribed, the backend refuses the message and tells the app to show the paywall.

## 10. What Actually Blocked Testing (Recap, Simple Version)

Since this caused a lot of back-and-forth, here's the plain summary of what was actually wrong, for the record:

1. **Package name mismatch** — the app and the Firebase Android registration had different package names. Fixed by aligning them.
2. **SMS region blocked** — Firebase blocks sending OTP text messages to certain countries by default, as an anti-fraud measure. Needed enabling in Firebase Console.
3. **Billing required** — Firebase now requires a **Blaze (pay-as-you-go)** plan attached to the project before it will even let you create a Firestore database, or send OTP SMS messages — even though normal usage still stays within free quotas. This is a Google policy, not something in our code.
4. **The Firestore database was never actually created** — because of #3, every attempt to create it silently failed, even though the Firebase Console sometimes showed a misleadingly "ready" looking screen.

None of these were bugs in the app's code — they were all one-time Firebase project setup/billing steps that only need to be done once, right at the start of a project's life.

## 11. Quick Glossary

| Term | Plain meaning |
|---|---|
| **Backend / server** | The "brain" program that runs somewhere other than the phone and does the sensitive work |
| **Endpoint / route** | One specific "door" on the backend the app can knock on (e.g. "send a message") |
| **Firestore** | Google's cloud database — where all the app's data (users, chats, etc.) is stored |
| **Collection / document** | Firestore's version of a "folder" and a "file" inside it |
| **Security rules** | The database's own bouncer — checks every request itself, independent of the app |
| **Admin SDK** | A special, trusted way for the *backend* (not the phone) to talk to Firebase with full permissions |
| **JWT session token** | Our own login system — the backend verifies an SMS OTP (via voicenSMS) and issues a signed token for sessions, instead of using Firebase Auth |
| **Webhook** | An automatic notification a service (like Razorpay) sends to our backend when something happens on their end |
| **Environment variable / `.env` file** | A place to store secret values (API keys, etc.) outside the actual code, so they're never accidentally shared |
| **Blaze plan** | Firebase's "pay-as-you-go" tier — required for some features even at zero actual cost |
